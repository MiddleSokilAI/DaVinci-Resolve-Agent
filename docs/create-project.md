# Створення проєкту з Project Manager

У режимі `auto` використовуйте наявний інструмент `resolve_create_project`:

```json
{
  "name": "Новий проєкт",
  "confirm_create": true,
  "idempotency_key": "unique-original-project-key",
  "timeout_seconds": 120
}
```

Якщо Resolve закритий, явний підтверджений `resolve_create_project` запускає
офіційний Resolve.exe один раз і чекає Project Manager в межах часу запиту.
Вікно, яке ще завантажується, також очікується без повторного запуску.
Запуск серіалізовано зі звичайним автоматичним підключенням. Якщо інший клієнт
уже володіє запуском, `PROJECT_STARTUP_BUSY` не займає ключ створення.
Якщо програма завершилася, змінився її процес або замість Project Manager
виявлено відкритий проєкт чи невідоме модальне вікно, холодне створення зупиняється.
Агент не перемикає цей проєкт і не закриває невідомі діалоги.

Єдиний виняток — точне вікно `Software Update` над Project Manager. Підтверджений
виклик створення автоматично натискає його перевірену кнопку `Skip` через UIA
InvokePattern і в межах того самого запиту чекає готовності Project Manager.
Адаптер двічі перевіряє єдиний офіційний процес Resolve, його час запуску,
ідентичність вікон і кнопки, відсутність інших видимих вікон та доступність Invoke.
Він не завантажує й не встановлює оновлення. Мінімізовані, змінені та неоднозначні
вікна залишаються заблокованими; миша, клавіатура й примусове фокусування не потрібні.

Skip виконується не більше одного разу за підготовку й лише до New Project/Create.
Якщо Skip не підтверджено, MCP повертає `PROJECT_STARTUP_UPDATE_BLOCKED`,
`uncertain: false` для створення і окреме `startup_update_dispatch_uncertain`
для дії Skip. Квитанція створення ще не публікується, початковий ключ не займається.
Завершений повтор із тим самим ключем не перевіряє та не пропускає діалог знову.
Успішна квитанція холодного створення містить `startup_update_skipped`: ця ознака
фіксує Skip у початковій операції. Під час історичного повтору вона не означає
нову дію з вікном оновлення; `ui_create_dispatched` залишається `false`.

Коли Resolve показує Project Manager, агент не запускає автоматичне
відкриття історичного проєкту. Фіксований внутрішній адаптер натискає New Project
через InvokePattern, встановлює назву через ValuePattern, читає її назад і
викликає Create. Селектори, назви кнопок і класи діалогу зафіксовано в коді;
MCP не приймає довільні UI-команди. Миша, клавіатура, Computer Use,
SetFocus, SetForegroundWindow та відновлення мінімізованого вікна не застосовуються.
Для запуску нового внутрішнього Lua-мосту меню розкриваються через
ExpandCollapsePattern, якщо він доступний, інакше через InvokePattern.
Точний пункт «Resolve Agent Marker» виконується через фіксований MSAA
DefaultAction: у перевіреній Qt-інсталяції UIA Invoke повертав успіх без
нативного запуску. Перед дією перевіряються процес, унікальна назва,
роль MenuItem, доступність, відома локалізована дія та SHA встановленого скрипту.
Після невизначеної відповіді інший API не викликається. Адаптер не задає фокус,
але сам провайдер меню Resolve може активувати вікно.
Доступне немінімізоване вікно приймається зі станом UIA `Running` або
`ReadyForUserInteraction`. `Closing`, `BlockedByModalWindow` та `NotResponding`
блокують дію. Перевірки процесу, вікна, кнопки й діалогу зберігаються.

Підтримується один вибраний локальний Disk-каталог, коренева папка guest і
перевірений профіль Project.db v17. Інші структури та неоднозначні імена
відхиляються до створення. Уже наявний проєкт не перезаписується.
Project Manager має бути доступний для фіксованого адаптера. Якщо налаштування
самого Resolve відновлюють останній проєкт під час запуску, цей холодний
маршрут відмовляється від створення; він не змінює налаштування Resolve.
Уже відкритий до початку запиту проєкт використовує наявний
нативний SDK-маршрут зі збереженням і резервною копією поточного проєкту.
`resolve_lua_create_project` зберігає вимогу до вже відкритого контексту;
для холодного створення використовуйте `resolve_create_project`.

Після закриття Resolve може залишити порожній незбережений `Untitled Project`.
Перед наступним підтвердженим створенням Python і Lua окремо перевіряють його
UUID, відсутність збереженого імені, таймлайнів, медіа й рендера. Такий шаблон
не зберігається як зайвий проєкт; створюється й зберігається лише запитаний.
Збережений або непорожній проєкт проходить звичайний шлях резервної копії.

Перед New Project, Create і запуском мосту агент зберігає квитанції.
Після невизначеного результату він не повторює ці дії. Повторний запит
повинен мати початковий ключ і назву: він перевіряє той самий процес і
покоління мосту. Інший ключ не обходить незавершену операцію; watcher,
відкриття інших проєктів і нативні записи заблоковано до її завершення.
Якщо початковий ключ залишився в `dialog_pending`, а діалогу немає, агент
спочатку перевіряє той самий процес і вікно Project Manager та незмінну
бібліотеку. Лише в цьому стані, до будь-якого Create, він може один раз за
виклик відновити New Project. Наявний діалог використовується без нового Begin.
Для `create_pending` і `bootstrapping` цей шлях недоступний: Create не повторюється.
Якщо до Create завершився весь процес Resolve, той самий ключ може запустити
новий процес лише після підтвердження, що Resolve зараз не запущений, а бібліотека
точно збігається з початковим знімком. Попередній процес зберігається в обмеженій
історії квитанції. Уже запущений сторонній процес не підхоплюється; після
можливого Create заміна процесу також заборонена.
Помилка фіксованого драйвера містить початкову причину й ознаку, чи міг уже
виконатися Invoke, замість загального `CREATE_UI_RESPONSE_UNVERIFIED`.

Завершений повтор повертає історичну квитанцію без UI-дій та без твердження
про поточне нативне з’єднання.

Якщо Create уже відправлено, але адаптер запуску мосту повернув помилку,
MCP зберігає невизначеність створення й показує причину окремо:

```json
{
  "code": "PROJECT_BRIDGE_BOOTSTRAP_FAILED",
  "cause_code": "MENU_ITEM_UNAVAILABLE",
  "uncertain": true,
  "bridge_dispatch_uncertain": false,
  "project_open_requested": false
}
```

`bridge_dispatch_uncertain: false` означає лише те, що ця спроба не запустила
міст. Це не підтвердження невдалого Create. Якщо немає слідів попереднього
нативного старту або завершення сесії, наступний виклик із початковими
назвою та ключем може повторити тільки запуск мосту в тій самій сесії;
New Project і Create не повторюються. Зміна назви вікна після створення блокує
новий запуск мосту; відповідність назви сама по собі не замінює нативну перевірку UUID.
Якщо запуск міг відбутися або його результат невідомий, ознака відправлення
залишається встановленою. Повтор читає початкову сесію без нового запуску мосту.
Це виправлення не підтверджує працездатність конкретного UIA-провайдера:
потрібні свіжа відповідь Resolve та перевірка збереження проєкту.

Відмова під час перевірок до New Project, зокрема
`PROJECT_MANAGER_STARTUP_TIMEOUT` або `PROJECT_CREATION_PREFLIGHT_TIMEOUT`, не створює
квитанції створення й не займає ключ. Після завершення запуску можна повторити
ту саму назву й початковий ключ. Це відрізняється від невизначеного результату
вже відправленого Create: такий виклик відновлюється лише за квитанцією.
Помилка підключення `NO_ACTIVE_PROJECT` не є передумовою відмови створення:
звіт можливостей позначає цей незалежний маршрут як `unverified` з причиною
`independent_creation_preflight_required`, не як доведене живе створення.

Успіх потребує свіжого Lua-підтвердження нового UUID, точної назви,
бібліотеки й кореневої папки. Агент також читає стабільні приватні копії
Project.db: новий UUID має бути збережений у вибраній бібліотеці, а набір
ідентичностей попередніх проєктів має залишитися тим самим. Живі SQLite-файли
не відкриваються для SQL-запису. Підпис вікна не доводить створення.

Новий проєкт може залишатися незбереженим після UI Create, тоді як стартовий
ExportProject потребує збереженого проєкту. Лише для підтвердженого створення
генерується окремий контекст: початкова назва, бібліотека та UUID усіх старих
проєктів. Lua перевіряє поточну назву, новий UUID, бібліотеку й кореневу папку,
викликає SaveProject та повторює перевірку перед експортом службового маркера.
Помилка збереження блокує запуск. Звичайне підключення такого контексту не має
і нічого автоматично не зберігає. Спожиту сесію не запускають і не зберігають знову.

Офлайн-тести виконують згенерований Lua 5.1 зі сценарієм, де експорт до SaveProject
неможливий; зміна проєкту, бібліотеки, папки, старий UUID і невдале збереження
блокують експорт. Окремо перевірено фіксований вибір MSAA без повторної дії,
одноразовий Create, втрату відповіді, конфлікти ключів і блокування watcher.

На Windows / Resolve Free 21.1.2 початкове живе створення на main `98c5856`
завершено після дозволеного операторського Save та фіксованого MSAA-запуску.
MCP підтвердив новий UUID, збереження в бібліотеці та повтор початкового ключа
без нового Create. Автоматичне виконання нового шляху з цього PR потребує
окремої живої перевірки після злиття; операторське відновлення її не замінює.

Робочу інсталяцію оновлюють лише після злиття в `upstream/main`. Кешовані MCP
процеси старих версій не отримують нову логіку під час зміни файлів на диску;
перед живою перевіркою потрібне оновлення їхнього процесу та watcher.
