# Відновлення після завершення процесу під час запуску рендера

Тайм-аут `StartRendering` не доводить, що рендер не стартував. Той самий ключ
не можна повторно запускати навіть після завершення процесу Resolve.

Якщо попередній Lua SDK `start_render_job` залишився `uncertain`, агент може
звільнити блокування для інших операцій лише після перевірки всіх умов:

- початковий процес із його PID і часом створення завершився; відмова в доступі
  або помилка системного запиту не є підтвердженням виходу;
- команда, ключ, fingerprint, покоління, сеанс, журнал і точний виклик
  `StartRendering` для початкового job збігаються;
- обидва зайняті пакети належать цій операції, немає пізньої нативної відповіді.

Для відсутнього PID додатково перевіряється системний список процесів.
Повторне використання PID відрізняється за часом створення. Живий початковий
процес, змінені докази та інші типи невизначених записів залишають блокування.

Агент зберігає початкові команду, відповідь і trace. Пакети переносяться цілими
до `retired-render-<command>/operation/inbox` та `rpc/inbox` у початковому runtime.
Журнал `render-exit-recovery` зберігає початкові записи й докази виходу; відновлення
після збою посеред перенесення використовує ці самі дані.

SDK-квитанція стає кінцевою помилкою `ORIGINAL_RENDER_PROCESS_EXITED` з
`native_outcome: unknown`, `retryable: false` та `render_not_restarted: true`.
Це не підтвердження успішного рендера. Повтор ключа повертає цю помилку до
підключення до Resolve, без відкриття проєкту чи повторного запуску job.
Файли експорту перевіряються окремо, а сама їхня наявність не змінює результат
нативної операції.

Відновлення виконується під наявним `operation.lock` перед холодним створенням /
відкриттям проєкту, ротацією мосту й обробкою SDK-команди. Воно не запускає Resolve,
не відкриває проєкти, не використовує UI та не змінює відеоматеріали.
